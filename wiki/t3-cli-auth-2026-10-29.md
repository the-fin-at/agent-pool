## T3s entscheidender Mechanismus

T3 Code ließ am genannten Stand bei leerem Claude-`homePath` die Providerumgebung unverändert; ein nicht gesetztes `CLAUDE_CONFIG_DIR` blieb deshalb tatsächlich ungesetzt. Nur ein bewusst gewähltes eigenes Profil setzte diese Variable. `HOME` blieb unverändert. Das erläutern [ClaudeHome.ts, Zeilen 12–42](https://github.com/pingdotgg/t3code/blob/08a463e29976617134de01e9341f898bc881d0eb/apps/server/src/provider/Drivers/ClaudeHome.ts#L12-L42) und die [offizielle Mehrkonten-Anleitung](https://github.com/pingdotgg/t3code/blob/08a463e29976617134de01e9341f898bc881d0eb/docs/user/providers-claude.md#L1-L36).

Der [Claude-Adapter, Zeilen 945–1043](https://github.com/pingdotgg/t3code/blob/08a463e29976617134de01e9341f898bc881d0eb/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts#L945-L1043) verwendete das offizielle Agent SDK und das ausgewählte Claude-Executable mit dessen Umgebung und Prozesspipes. Die native Laufzeit erledigte die Authentifizierung; zur Wiederverwendung des normalen Logins brauchte T3 keinen eigenen OAuth-Token-Proxy. Codex lief über den [App-Server-Adapter](https://github.com/pingdotgg/t3code/blob/08a463e29976617134de01e9341f898bc881d0eb/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L1492-L1507). Der T3-Quellcode wurde nur gelesen, nicht ausgeführt.

## Tatsächlicher Unterschied auf Johannes' Mac

Die read-only Abfrage `claude auth status` mit Claude Code 2.1.312 bestätigte am 2026-10-29 die vorhandene normale Claude.ai-Max-Anmeldung. Die Binärdatei hatte SHA-256 `6b5ec691195e551b02c41df9f7d723f4ea61eaa03c2df90acefe3736f1aeb620`. Ein gezielter A/B-Vergleich ergab:

| Statusumgebung | Exit | loggedIn / authMethod | Plan |
| --- | --- | --- | --- |
| Normale Umgebung, Variable nicht gesetzt | 0 | true / claude.ai | max |
| Fleet-bereinigte Umgebung, Variable nicht gesetzt | 0 | true / claude.ai | max |
| Normale Umgebung, ausschließlich `CLAUDE_CONFIG_DIR=$HOME/.claude` ergänzt | 1 | false / none | null |
| Fleet-bereinigte Umgebung plus dieser expliziten Variable | 1 | false / none | null |
| Normale Umgebung ohne Variable erneut geprüft | 0 | true / claude.ai | max |

Alle Fälle meldeten denselben effektiven Konfigurationspfad `$HOME/.claude`, und `HOME` blieb unverändert. Auf diesem Mac war also „Variable weglassen“ nicht gleichbedeutend mit „dieselbe Standarddir explizit setzen“. Der Test isolierte diese Variable als Unterschied; die genaue native Keychain-Namensbildung wurde nicht untersucht. Daraus folgt keine plattformübergreifend bestätigte Keychain-Erklärung.

Sanitisierte lokale Belege wurden unter `/private/tmp/fleet-existing-claude-auth-{status,explicit-status,ab-status,runtime}-20261029.json` gespeichert. Die Tabelle bewahrt das Ergebnis unabhängig von diesen temporären Dateien. Keine E-Mails, Codes, Tokens oder Credential-Inhalte wurden ausgegeben oder gespeichert; es gab keine Anmeldung, Registrierung, Inferenz oder produktive Änderung.

## Abgeleiteter nächster Schritt, nicht umgesetzt

Ein eigener Modus „Bestehende CLI-Anmeldung verwenden“ sollte die normale CLI-Anmeldung erkennen und prüfen, ohne bei normalem Standardkontext `CLAUDE_CONFIG_DIR` neu zu setzen. Statusprüfung und spätere Auftragsausführung müssten dieselbe Authumgebung verwenden. Die bisherigen Filter gegen unerwartete API-Abrechnung sollten erhalten bleiben. Zusätzliche Accounts könnten weiterhin ausdrücklich getrennte Verzeichnisse verwenden. Ein Remote-Account müsste auf dem ausführenden Server vorhanden sein; ein Mac-Login meldet Linux nicht automatisch an.

Vor Umsetzung müssten Tests die Fälle ungesetzt/Defaultdir explizit/eigene Dir, fehlender Login, Accountwechsel/Logout und gleichbleibende Umgebung zwischen Status und Auftrag abdecken. Pfaddeduplizierung verhindert keine doppelt gezählte Provideridentität in verschiedenen Verzeichnissen; Quoten-, Wechsel- und Locksemantik brauchen deshalb eine bewusste Regel. Normale externe CLI-Prozesse beachten Fleets Verzeichnislock nicht. Das sind Anforderungen an die vorgeschlagene Integration, keine in dieser Untersuchung zusätzlich bewiesenen Schedulingfehler. Externen Accountwechsel/Logout und Entfernen einer Fleet-Referenz dürfte die Oberfläche nicht mit Löschung externer Credentials verwechseln.

Diese Untersuchung ändert weder die erfolgreiche isolierte Anmeldung noch den gemergten 0.5.1-Retry-Fix. Die Ursache des ursprünglichen Loginversuchs bleibt gemäß [Incident-Notiz](claude-login-2026-10-29.md) unbewiesen.
